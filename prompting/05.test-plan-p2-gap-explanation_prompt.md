## 1. test_plan에서 진짜 P2인 것

RTM(§9) 기준으로 **P2는 사실상 한 줄**입니다.

| REQ | 대표 TC | 우선순위 |
|-----|---------|----------|
| §0.1 Tuner 계약 | `CH-INV*` (+ `TunerTest` 참조) | **P2** |

TDD 로드맵(§10)에서도 이 묶음은 **6단계(마지막)** 입니다.

그래서 `CH-INV-02`(99 상한 정상)처럼 **이미 다른 TC로 검증된 경계**는 의도적으로 뒤로 미뤘고, `CH-INV-01`·`CH-INV-03`만 넣었습니다.

- **CH-INV-02**: `CH-02`/`CH-04`에서 `"99"` 커밋을 이미 검증 → 중복
- **커버리지 90%+**: 이번 작업 범위 밖(계획서에도 “선택”)

## 2. 보고서에 P2라고 적었지만, plan상으론 P1인 것

`04.tv-controller-tests_report.md`의 “P2 미구현” 목록 중 상당수는 RTM상 **P1**입니다.

| 미구현 TC | plan 우선순위 | 미구현 이유 (실무적) |
|-----------|---------------|----------------------|
| **FAV-A03~A06** | P1 (FAV-A*) | 선호 목록이 private → `setCH` 0회만으로는 “목록에 6이 들어갔는지” 직접 검증 어려움. A01/A02/A07 + `FAV_NEXT`로 **간접** 커버 |
| **FAV-C05, C06** (×5, ×10) | P0 연속 | C01~C04, C10~C13로 **알고리즘·wrap은 이미 검증**. C06은 호출 10회 반복이라 **로직 중복·스텁만 길어짐** |
| **SEEK-03** | P1 | `TunerTest::testSeekCh10times` 영역. plan도 “TunerTest 참조” → **TunerTest.cpp에 이미 있음** |
| **SEEK-04** | P1 | SEARCH 2회 시 “덮어쓰기 vs 누적” **정책 고정 TC**. SEEK-01 + 구현(매번 `clear` 후 재검색)으로 동작은 맞지만 **전용 TC 없음** |
| **UD-T02** | P1 | 일반 업(6→7) → SEARCH → 목록 업(→14) **전환 시나리오**. UD-T01 + UD-S*로 **부분** 커버 |
| **E2E-02, E2E-03** | §8 복합 | 단위·부분 E2E(E2E-01, E2E-04)만 우선. 전체 플로우는 **조합 테스트**라 1차 Green 목표에선 생략 |

출구 기준(§11.2)도 **“P0·P1 TC 100% Pass”**이지, plan의 모든 TC-ID 100%는 아닙니다.

## 3. 당시 작업 목표와의 관계

당시 요청은:

> `test_plan` 참고 → **테스트 코드 완성** → **`ctest` Green**

그래서 구현 순서는 plan §10과 같이 **1~4단계(P0/P1 핵심)** 위주였습니다.

- 숫자/선호/업다운/검색의 **대표·경계·연속(FAV-C)** 위주로 ~68개 + 파라미터 6개
- **5~6단계**(복합 E2E 전부, INV 나머지, 커버리지)는 “Green + P0/P1 대표” 달성 후 **의도적 잔여**

즉, **버그가 있어서 못 만든 것**이라기보다, **우선순위·중복·관측 난이도** 때문에 1차 범위에서 뺀 것에 가깝습니다.

## 4. 정리

| 구분 | 요약 |
|------|------|
| **진짜 P2** | `CH-INV*` 나머지, gcov — 로드맵 6단계, 일부는 중복이라 생략 |
| **보고서 “P2” 표기** | P1·복합 TC까지 묶어서 “후속”으로 적은 것 — RTM과 1:1은 아님 |
| **기술적 이유** | 내부 상태 비노출(FAV-A03~06), TunerTest와 역할 분리(SEEK-03), 반복 스트레스만 추가(FAV-C06) |
