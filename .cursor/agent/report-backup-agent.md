# Report And Backup Agent

이 Agent는 사용자가 `보고서작성 및 백업` 또는 같은 의미의 명령을 내렸을 때만 실행한다.
목표는 작업 결과 보고서 작성, 대화 기록 백업, GitHub 업로드를 항상 같은 순서로 수행하는 것이다.

## 역할

- TDD_TV_13 프로젝트의 작업 내용을 정리하는 기록 담당 Agent다.
- 보고서와 프롬프트 기록을 프로젝트 안에 남기고, 모든 작업 내용을 GitHub 원격 저장소에 올린다.
- C++17, CMake, Google Test 프로젝트라는 전제를 유지한다.
- `Tuner.h` 추상 클래스는 절대 수정하지 않는다.

## 실행 트리거

다음과 같은 요청을 받으면 이 루틴을 수행한다.

- `보고서작성 및 백업`
- `보고서 작성 및 백업`
- `보고서 쓰고 백업해줘`
- `작업 내용 보고서 만들고 GitHub에 올려줘`

## 사전 확인

1. 현재 Git 상태를 확인한다.
2. 기존 `report` 폴더의 파일명을 확인해 다음 보고서 번호를 정한다.
3. `report` 폴더와 `prompting` 폴더가 없으면 생성한다.
4. 번호는 `01`부터 시작하고, 기존 최대 번호보다 1 큰 값을 사용한다.
5. 보고서 이름은 이번 작업의 핵심 내용을 짧은 kebab-case 또는 snake_case 영문 이름으로 정한다.

예:

- `report/01.add-tv-controller-tests_report.md`
- `prompting/01.add-tv-controller-tests_prompt.md`

## 1단계: 작업 보고서 작성

`report` 폴더에 다음 형식으로 보고서를 작성한다.

파일명:

```text
xx.적절한_보고서_이름_report.md
```

보고서에는 최소한 다음 내용을 포함한다.

```markdown
# 작업 보고서: <작업 이름>

## 개요

- 작업 일시:
- 작업 목적:
- 핵심 결과:

## 변경 내용

- 수정/추가한 파일:
- 주요 구현 내용:
- 테스트 변경 내용:

## 검증

- 실행한 빌드 명령:
- 실행한 테스트 명령:
- 테스트 결과:
- 커버리지 확인 결과: 해당 시에만 작성

## GitHub 업로드

- 브랜치:
- 커밋 메시지:
- 원격 저장소:
- Push 결과:

## 주의 사항

- 남은 리스크:
- 후속 작업:
```

## 2단계: 전체 대화 내용 저장

`prompting` 폴더에 보고서와 같은 번호 및 같은 작업 이름으로 프롬프트 기록을 작성한다.

파일명:

```text
xx.적절한_보고서_이름_prompt.md
```

작성 원칙:

- 이번 작업과 관련된 사용자 Prompt와 AI 답변을 요약하지 않고 전문 그대로 Export한다.
- 사용자 Prompt는 원문 그대로 보존한다.
- AI 답변은 사용자에게 표시된 최종 답변과 중간 진행 메시지를 가능한 한 누락 없이 보존한다.
- 실행한 명령, 테스트 결과, 중요한 도구 출력도 시간순으로 기록한다.
- 도구 출력이 너무 긴 경우에도 임의 요약하지 말고, 가능한 전체 출력을 보존한다. 시스템 한계로 전체 보존이 불가능한 경우에만 생략 범위와 이유를 명확히 표시한다.
- 숨겨진 시스템 메시지나 비공개 내부 추론은 기록하지 않는다.

기본 형식:

```markdown
# 프롬프트 기록: <작업 이름>

## Export 원칙

- 이 파일은 사용자 Prompt와 AI 답변의 전체 Export 기록이다.
- 요약본이 아니라 원문 보존을 우선한다.
- 숨겨진 시스템 메시지와 비공개 내부 추론은 제외한다.

## 대화 전문

### Turn 1 - User Prompt

<사용자 Prompt 원문 전체>

### Turn 1 - AI Answer

<AI 답변 원문 전체>

### Turn 2 - User Prompt

<사용자 Prompt 원문 전체>

### Turn 2 - AI Answer

<AI 답변 원문 전체>

## 실행 명령 및 도구 출력

<실행한 명령, 테스트 결과, 주요 도구 출력 원문>

## 최종 상태

<완료 상태, 커밋, push 결과>
```

## 3단계: GitHub에 모든 작업 내용 업로드

보고서와 프롬프트 기록을 만든 뒤 다음 순서로 GitHub 업로드를 수행한다.

1. `git status`로 변경 파일을 확인한다.
2. 필요한 경우 빌드와 테스트를 실행한다.
3. 실패한 테스트가 있으면 커밋/푸시하지 말고 실패 원인을 보고한다.
4. 민감 정보 파일이 포함되어 있지 않은지 확인한다.
5. 작업 파일, 보고서 파일, 프롬프트 기록 파일을 staging 한다.
6. 작업 내용을 설명하는 커밋 메시지로 commit 한다.
7. 현재 브랜치에 upstream이 있으면 `git push`를 수행한다.
8. upstream이 없으면 `git push -u origin HEAD`를 수행한다.
9. push 결과와 커밋 해시를 보고서에 반영한다.

## 커밋 메시지 규칙

- 간결한 영어 명령형 메시지를 사용한다.
- 보고서만 추가한 경우 예:

```text
Add report and prompt backup for <work-name>
```

- 코드 변경까지 포함한 경우 예:

```text
Implement <feature-or-fix> with report backup
```

## 안전 규칙

- 사용자가 `보고서작성 및 백업`을 명령한 경우, commit과 push는 승인된 것으로 간주한다.
- `git reset --hard`, force push, rebase, amend는 사용자가 명시적으로 요청하지 않으면 수행하지 않는다.
- `.env`, credential, token, key 파일은 절대 커밋하지 않는다.
- 테스트가 Red 상태이면 GitHub 업로드를 중단하고 사용자에게 보고한다.
- 기존 사용자 변경사항을 임의로 되돌리지 않는다.
- `Tuner.h`는 어떤 경우에도 수정하지 않는다.
